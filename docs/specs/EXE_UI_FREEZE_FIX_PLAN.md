# EXE 无响应与卡顿修复计划

日期：2026-09-24  
范围：GUI REV04 Windows EXE 的启动、端口刷新与串口连接响应性  
状态：2026-09-28 已完成本轮复现的页面切换/缩放阻塞修复及端口枚举后台化；详见 `EXE_UI_FREEZE_FIX_RESULT.md`。

## 2026-09-28 范围与证据更新

用户补充：页面切换及放大/缩小也出现无响应。本轮据此改用完整离线 Tk 场景定位：30 次页面/模式/尺寸切换中的最大事件循环间隔为 1575.96 ms；AWP1018/AWP1221 的模式布局回调在 `after_idle` 内调用 `update_idletasks()`，同步耗尽全部布局/重绘工作，造成 1.2–1.5 秒的单次回调阻塞。

已移除这两个模式布局回调和首页尺寸对齐中的嵌套空闲循环；保留已有 Configure 事件完成后续几何同步。首页端口枚举改为单个后台工作线程和主线程结果队列。最终相同 30 步检查最大事件循环间隔为 497.37 ms，10 个模式最大化/还原几何检查、114 项单元测试及新版 EXE 的 36 次响应检查通过。

以下串口方案保留为 2026-09-24 的静态排查记录。连接握手和各芯片页面的同步通信不属于本轮已复现的布局根因，也没有通过本轮离线布局验证获得真机验收。

## 现象与判断

用户反馈当前生成的 EXE 会出现“无响应”或卡顿。检查当前工作区后，发现多处串口相关操作仍在 Tk 主线程同步执行，存在可直接解释界面冻结的路径：

1. `core/serial_manager.py` 的 `SerialManager.list_port_info()` 在 Windows 上没有枚举到端口且 `probe_missing=True` 时，会逐个尝试打开 COM1–COM256。串口配置的 50 ms 是读写超时，不能作为打开端口的耗时上限。原 `HomePage.__init__()` 和切回首页时会同步等待端口枚举；本轮已将枚举移到后台。
2. `app/application.py` 的 `HomePage.toggle_connection()` 在 Tk 回调里同步调用 `SerialRouter.connect()`。`SerialManager.connect()` 执行 READY/CAP 握手，等待上限为 30 秒。
3. 连接成功后，`_finish_connection_when_ready()` 在 Tk 主线程同步运行支持芯片发现和 CAP 能力查询。发现会对多个地址发起串口读操作，单个读超时可达 0.8 秒。
4. Home 页的 GPIO、ADC、频率、I2C 速度和手动寄存器读写回调也有同步串口调用。失联或设备响应慢时，这些操作会让界面短暂停顿。

`styles/fonts.py` 中历史上可能造成启动阻塞的 `SendMessageW(HWND_BROADCAST, WM_FONTCHANGE, ...)` 已经不存在，不是当前源码中的触发点。

## 实施方案

### 第一阶段：解除启动与连接冻结

1. 将端口枚举及 Windows COM 兜底扫描移至后台线程。工作线程只调用串口层并写入有界结果队列；Tk 主线程通过短间隔 `after()` 轮询并更新控件。限制并发刷新，丢弃过期结果，并在 Home 页销毁时取消 UI 轮询。
2. 将 `SerialRouter.connect()` 移至后台线程。连接按钮进入忙碌/禁用状态；主线程轮询队列处理完成、失败和错误提示，整个握手期间保持窗口可响应。
3. 将连接后的芯片发现和 CAP 查询合并到后台串口工作中。工作线程不访问 Tk 控件或 `AppState`；通过结果队列将身份、错误和能力结果交给 Tk 主线程应用。
4. 用连接代次/请求令牌校验结果，防止用户断开、切换端口或关闭窗口后，迟到结果更新新会话或已销毁界面。

### 第二阶段：解除 Home 页手动串口操作冻结

将 GPIO 配置/读取、ADC、频率、I2C 速度和手动寄存器读写统一改为后台串口工作与主线程结果应用。保留现有输入校验、协议解析、成功状态更新和错误对话框行为；同一个 Home 操作入口应防止重复点击启动重复命令。

本阶段只处理 Home 页明确可见的板卡工具与寄存器工具。其他芯片页面的同步串口操作不在第一版改动范围内；若用户反馈仍集中在某个页面，再据此扩展，避免一次性改写大量页面事务语义。

## 验收标准

1. 无串口设备且 Windows 兜底扫描触发时，窗口仍可拖动、切换页面和关闭。
2. 连接一个不发送 READY/CAP 的端口时，等待握手期间窗口仍可响应；超时后显示现有错误信息并恢复连接按钮。
3. 成功连接时，芯片发现与 CAP 检查运行期间窗口仍可响应，最终显示正确的设备/能力状态。
4. Home 页串口读写遇到超时期间，窗口仍可响应；完成后 UI 状态和错误提示正确。
5. 端口切换、快速断开/重连及关闭窗口时，后台迟到结果不更新错误会话，也不触发 Tk 销毁异常。
6. 保留当前工作区已有用户改动；只修改与响应性直接相关的代码和回归验证。

## 验证建议

- 增加可控假串口管理器测试：让端口扫描、连接、芯片发现和普通 Home 操作分别延迟，并断言 Tk 主线程调度/控件回调可在工作仍运行时继续执行。
- 覆盖连接失败、端口切换、断开重连、销毁窗口后的迟到结果。
- 运行相关单元测试和启动回归测试；构建 EXE 后在无串口、慢/无响应串口条件下手工验证交互响应。
- 报告区分源码/测试/EXE 构建验证与真实板卡验收，不把假串口验证表述成硬件验收。
